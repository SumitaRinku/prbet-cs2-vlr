# 03 · 数据库设计

- 引擎：SQLite（better-sqlite3，**同步** API），库文件 `data/database.sqlite`（gitignore）。
- 连接：`server/config/database.js` 模块级单例，加载时自动创建 `data/` 目录，`db.pragma('foreign_keys = ON')` 启用外键。
- 建表与迁移：`server/config/init-db.js` 的 `ensureDatabase()`，`CREATE TABLE IF NOT EXISTS` + `PRAGMA table_info` 列探测式幂等迁移，**每次启动都会执行**。

## 实体关系（ER）

```
users ──────┐
            │ 1        N
            └──────── predictions ──────── matches ──────── tournaments
                        │  N      1         │  N      1        │
                        │                     │                  │
                        │（predicted_winner）  │（team1/team2）    │
                        ▼                     ▼                  ▼
                      teams ◄─────────────────┘                 sync_runs
                                                                  （独立审计表）
```

- 一个用户对一场比赛**最多一条**预测：`predictions UNIQUE(user_id, match_id)`。
- 删除赛事 → 级联删除其比赛与预测（`ON DELETE CASCADE`）；删除被比赛引用的队伍同样级联。
- 删除用户 → 级联删除其预测（管理端删用户后会 `recalculateUserScores()` 重建总分）。

## 索引

```sql
-- 幂等 upsert 的定位键（部分唯一索引：仅 external 来源数据）
CREATE UNIQUE INDEX idx_tournaments_external ON tournaments(external_source, external_id)
    WHERE external_source IS NOT NULL AND external_id IS NOT NULL;
CREATE UNIQUE INDEX idx_teams_external       ON teams(external_source, external_id)       WHERE ...;
CREATE UNIQUE INDEX idx_matches_external     ON matches(external_source, external_id)     WHERE ...;

-- 常用查询路径
idx_matches_time        ON matches(match_time)
idx_matches_status      ON matches(status)
idx_matches_tournament  ON matches(tournament_id)
idx_teams_game          ON teams(game_type)
idx_predictions_user    ON predictions(user_id)
idx_predictions_match   ON predictions(match_id)
```

## 启动迁移机制（init-db.js · ensureDatabase）

每次进程启动（`server/index.js`、`npm run init-db`、CLI 同步前）都会执行：

1. **建表**：六张表 + 索引全部 `IF NOT EXISTS`，空库与老库都安全。
2. **列迁移**（探测-补列，幂等）：
   - `teams.game_type`
   - `tournaments.is_active`、`name_locked`（顺带把 pandascore 来源全置 1）、`logo_url`
   - `matches.stage_name`、`stage_slug`、`stage_external_id`、`is_forfeit`
3. **历史弃权局回填**（一次性事务，幂等）：
   - 目标：`is_forfeit=0 AND status='cancelled' AND winner_team_id IS NOT NULL` 的旧数据（旧逻辑把 PandaScore「canceled + winner」弃权局记成 cancelled 不结算，且已超出 1 天同步回看窗口，常规同步不会再触及）。
   - 动作：改为 `is_forfeit=1, status='finished', 1-0 比分, betting_enabled=0`，逐场 `settleMatch()`（0 分结算），最后 `recalculateUserScores()`。
   - 幂等性：修正后 `is_forfeit=1` 不再命中 WHERE，重复启动无副作用。
4. **默认管理员**：`ADMIN_USERNAME`（默认 `admin`）不存在则创建；密码取 `ADMIN_PASSWORD` 或随机 12 字节 base64url（仅控制台打印一次）。

## external_id 规范与升级

早期版本 external_id 不带游戏前缀（裸 PandaScore id），引入双游戏后规范为 `<game_type>:<id>`。兼容逻辑：

- `pandascoreService.findOrUpgradeExternalId(table, canonicalId, gameType, now)`：先按规范 id 查；查不到且规范 id 带前缀时，按**裸 id** 再查，命中则原地升级为规范 id。
- 遗留的重复数据（老 id 与规范 id 并存）由 `scripts/cleanup-pandascore-duplicates.js` 一次性清理（迁移预测 → 删旧比赛/赛事/无引用队伍 → 重算积分）。

## 数据完整性要点

- **总分是重建值不是累加值**：`users.total_score` 只能经 `recalculateUserScores()`（清零 + SUM(points_earned) 回填）修改，任何写预测/比赛/用户的删除路径之后都要调用，防止增量漂移。
- **points_earned 的三态**：`NULL`（比赛未结束/未结算）、`0`（结算为 0 分）、`>0`（得分）。排行榜用 `COUNT(CASE WHEN m.status='finished' AND m.is_forfeit=0 ...)` 区分统计口径。
- **弃权局不入统计**：胜率、H2H、队伍履历、榜单得分率全部带 `is_forfeit = 0` 过滤。
