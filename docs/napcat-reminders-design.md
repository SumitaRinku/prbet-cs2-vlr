# QQ 群赛事提醒：数据库审阅与接入设计

审阅日期：2026-09-21。本文保留最初的架构设计讨论。现已完成第一版代码，实际配置和操作以 [Windows / Linux 部署教程](../bot/README.md) 为准；尚未连接生产服务器或向真实群发送消息。

第一版差异：每日消息已增加昨日简要赛果；Windows 采用零依赖 Node.js 程序与原子保存的本地 JSON 发送记录（不是下文设想的 SQLite）；接口一次完整返回，超过 10,000 场显式报错（不是分页）；按游戏的同步状态表名为 `bot_sync_state`；订阅的任一游戏过期时暂停本轮推送；赛程更正每分钟检查，暂不做五分钟合并。下文的环境变量配置草案已由 `bot/config.example.json` 代替。

## 1. 审阅结论

现有 SQLite 足够提供赛程内容，不需要迁移到 MySQL。推荐在 Linux 网站新增专用赛程接口，在 Windows 上运行独立 Node.js 推送程序，调用本机 NapCat 的 OneBot HTTP 接口。

```text
Linux：PandaScore → 网站同步服务 → SQLite → HTTPS 只读赛程接口
                                               ↑ Windows 每 60 秒拉取
Windows：推送程序 + 本地发送记录 → 本机 NapCat → QQ 群
```

SQLite 是本地文件，NapCat 本身不负责数据库查询、定时任务和消息排版。不要通过 SMB、文件同步或把数据库下载到 Windows 的方式共享在线库。Windows 主动访问网站，不需要 Linux 主动连接 Windows，也不需要公开 NapCat 端口。

### 可直接复用的数据

| 表 | 关键字段 | 推送用途 |
| --- | --- | --- |
| `matches` | `id`, `tournament_id`, `team1_id`, `team2_id`, `match_time`, `status`, `format`, `stage_name`, `betting_enabled`, `last_synced_at` | 对阵、时间、BO、阶段和预测入口提示 |
| `tournaments` | `name`, `short_name`, `game_type`, `is_active`, `tier`, `begin_at`, `end_at` | 赛事名称、游戏分类、范围筛选 |
| `teams` | `name`, `short_name`, `external_id` | 队名及 TBD 识别 |
| `sync_runs` | `status`, `message`, `finished_at` | 同步运行诊断；目前不足以准确判断每个游戏的数据新鲜度 |

通知接口不需要读取或返回用户、密码、JWT、个人预测数据。

### 本地只读检查结果

- 1,788 场比赛、916 支队伍、48 个赛事，其中 30 个赛事启用。
- `finished` 1,374 场、`ongoing` 23 场、`upcoming` 391 场；185 场包含 TBD。
- 比赛时间范围为 2026-05-04 至 2026-09-12（UTC），最新同步结束于 2026-09-05 18:01:58 UTC。
- 存在 8 月份仍标记 `upcoming` 的记录。以上只代表当前工作区，不能据此判断 Linux 生产库是否过期。
- 本次未发现 SQLite 无法解析的比赛时间；但数据库列为 TEXT，没有数据库级时间格式约束。

### 实施前需要解决的语义问题

1. **时间缺失会伪装成当前时间。** `pandascoreService.js` 使用 `iso(match.scheduled_at || match.begin_at) || now`。新增 `matches.time_confirmed INTEGER NOT NULL DEFAULT 0`，仅在源时间有效或管理员明确设置时间时置 1；同步缺失时置 0。旧数据默认待重新同步或人工确认，不能用 `match_time = last_synced_at` 来可靠反推。
2. **不能只按状态筛选。** 临赛提醒要求状态为 `upcoming`、开赛时间严格晚于当前时间、时间已确认、赛事已启用、双方队伍已确定。过期 `upcoming` 不提醒。
3. **同步部分失败也写成 success。** 当前某个游戏拉取失败时，`sync_runs` 仍可能是 `success`，失败信息放在 `message`。建议新增 `sync_source_state(source, game_type, last_success_at, last_error_at, last_error)`，以 `(source, game_type)` 为主键；对应游戏完整拉取且数据库事务提交成功后才更新成功时间。
4. **时间格式需要统一。** 比赛同步时间通常为带 Z 的 ISO UTC，SQLite `CURRENT_TIMESTAMP` 为无时区后缀的 UTC；管理员接口会直接存入传入时间。新接口统一输出 ISO UTC，拒绝无时区的比赛时间输入；Windows 以 `Asia/Shanghai` 计算每日窗口，不依赖服务器系统时区。
5. **新同步赛事默认禁用。** 当前同步插入 `tournaments.is_active = 0`。默认通知沿用后台启用状态，新增赛事需先在后台启用。
6. **赛事开幕时间不总是可靠。** `tournaments.begin_at` 可能回退到某场比赛时间。周预告以未来七天实际已知赛程为依据，不把该字段直接当成官方开幕时间。
7. **现有比赛列表有 200 条上限，且缺少专用时间窗口。** 不应直接把通用 `/api/matches` 当完整通知源，否则历史数据和截断可能导致漏发。

## 2. 默认消息规则

日报发送规则已按用户要求调整：默认 12:00，非凌晨的早场提前 10 分钟发送，包含次日凌晨赛程，无比赛则展示后续预告。统一北京时间，支持 CS2 / Valorant，默认仅后台启用赛事，不额外按 tier 过滤。“凌晨”暂定 00:00–05:59，06:00 分界为可配置默认值。

| 类型 | 时机 | 内容与范围 |
| --- | --- | --- |
| 每日赛程 | 默认每天 12:00；当天 06:00（含）至 12:00（不含）有比赛时，改为最早一场开赛前 10 分钟 | 当天 06:00（含）至次日 06:00（不含），按游戏、赛事、时间排列；次日凌晨明确标注日期 |
| 无比赛日预告 | 当天 12:00，替代当日日报 | 当前日报窗口无有效比赛时，展示其后、发送时刻起未来 7 天内的已知赛事与最近对阵 |
| 开赛提醒 | 开赛前 30 分钟 | 已确认对阵与时间的未开始比赛；每分钟扫描，剩余时间大于 0 且不超过 30 分钟，显示实际剩余分钟 |
| 每周预告 | 周日 20:00 | 发送时刻至未来 7 天的已知赛程，按赛事汇总，列日期范围、场次及最早几场对阵 |
| 赛程变更 | 已通知比赛发生变化时 | 提醒改期、取消或对阵更换；同一比赛 5 分钟内的变化合并一次 |

默认不 @全体成员、不发送赛果、不回复群聊指令。同步异常时不能把缺失数据解读为“没有比赛”；只有所有订阅游戏数据新鲜且分页拉取完整，才能判定无比赛并切换后续预告。未来七天也没有已知比赛时，发送“今日暂无比赛，未来七天暂无已公布赛程”，不虚构赛事。

### 日报日期与发送时刻

- 日期 D 的日报窗口为 `[D 06:00, D+1 06:00)`；D 当天凌晨归入 D-1 日报，D+1 凌晨归入 D 日报。即使 D 白天没有比赛，只要 D+1 凌晨有比赛，也发送这份日报，不切换到无比赛日预告。
- 在各群订阅范围内查找 D 当天 `[06:00, 12:00)` 最早的有效比赛 E；有则发送时刻为 E 减 10 分钟，否则为 D 当天 12:00。仅时间确认且非取消、非延期的比赛影响提前发送；已知时间但对阵待定的比赛可列为 TBD，也可影响提前发送。
- 例如最早 09:00 开赛，则 08:50 发完整日报；最早 11:55 开赛，则 11:45 发；最早 12:00 开赛，则仍在 12:00 发；当天只有次日 02:00 的比赛，则当天 12:00 发。
- 每个日期只生成一份日报（超长可分段）；提前发过后 12:00 不重复发送。日报与无比赛日预告共用同一个日期去重键，后续新增或改期只触发更正。
- 每分钟依据最新赛程重算尚未发送的日报时刻；调度需要同时考虑当天与次日的日期键，确保次日 06:00 的比赛可在 05:50 提前触发。推送日期不能简单由当前时间减 6 小时决定。
- 若同步较晚或停机错过计划时间，遵循补发窗口；补发内容保留整份日报范围，已过时间的比赛标注实际状态，状态仍为 upcoming 则标“已过计划时间”，不据此推断已经开赛。
- 次日凌晨使用“次日 09/23 02:00”样式，避免仅显示 02:00 产生歧义。跨午夜的独立临赛提醒仍按开赛前 30 分钟触发。

无比赛日预告按赛事分组，展示日期、游戏、赛事名、最近几场已知对阵及详情链接；已知比赛时间而对阵未定时标注 TBD。它是当日日报的替代内容，原定周日 20:00 周预告仍为单独的可配置功能。

### 日报示例（虚构赛程）

```text
【今日赛事 · 09/22 周二】
时间：北京时间
范围：09/22 06:00—09/23 06:00（不含）

CS2 · 示例赛事
18:00  Team A vs Team B · BO3
21:30  Team C vs Team D · BO3
次日 09/23 02:00  Team G vs Team H · BO3

Valorant · 示例赛事
19:00  Team E vs Team F · BO5 · 决赛

赛程可能调整，以最新公告为准。
赛事详情：https://你的站点/tournaments.html
```

### 临赛提醒示例（虚构赛程）

```text
【即将开赛 · 约 30 分钟后】
CS2 · 示例赛事 · 半决赛
Team A vs Team B · BO3
09/22 18:00（北京时间）
赛事详情：https://你的站点/tournaments.html?tournament=123
```

只有 `betting_enabled = 1` 且尚未开赛时才附加“赛前可参与预测”，比赛是否提醒不受预测开关控制。

第一版使用纯文本消息段，不使用可被解释为 CQ 码的拼接字符串；每条建议最多约 1,200 字，超长按赛事拆分并编号，每群发送间隔至少 3 秒。周预告明确注明“仅包含目前已同步的未来七天赛程”，不是完整赛事日历。

## 3. Linux 网站改动

新增 `GET /api/bot/schedule?from=<ISO UTC>&to=<ISO UTC>&cursor=...`：

- 使用独立 `BOT_FEED_TOKEN`，请求头 `Authorization: Bearer ...`，不复用管理员 JWT；未配置时关闭接口。
- 仅 HTTPS 使用；限制请求频率、时间范围（最大 8 天）和每页数量。以时间与 ID 稳定排序并返回下一页游标，Windows 收齐所有页面后才生成汇总。
- 返回 `generated_at`、按游戏划分的同步状态、赛事与比赛白名单字段。响应设置 `Cache-Control: no-store`。
- 包含窗口内的已启用赛事赛程和明确状态；TBD 可用于周预告的“待定对阵”统计，临赛发送端必须排除。
- 对已发送过但移出查询窗口的比赛，提供按 ID 批量查状态的接口，例如 `GET /api/bot/matches?ids=...`，限制最多 100 个 ID，以便识别改期、取消、禁用或删除。删除/禁用要返回明确的不可用标识，不能无限等待。
- 保留原有比赛查询索引；新增索引前先通过实际查询计划验证，无需先行改动业务主键和外键。

数据新鲜度默认阈值建议为 20 分钟（现有同步默认每 5 分钟）：PandaScore 来源需同时满足对应游戏完整同步较新、比赛记录最近同步较新；手工录入比赛按人工确认时间逻辑处理，不套用 PandaScore 同步要求。某游戏过期时暂停该游戏推送并记本地告警；新鲜游戏可以继续，汇总说明另一游戏暂缺。发送前重新校验，避免用长时间缓存触发临赛消息。

## 4. Windows 推送程序

建议项目下新增独立 `bot/` 目录，独立依赖和配置，只需 Node.js 20+；使用任务计划程序在开机后启动并在退出后重启，设置禁止并行实例、固定工作目录。无需安装完整网站依赖。

配置项：

```dotenv
SITE_BASE_URL=https://你的站点
BOT_FEED_TOKEN=与网站一致的独立随机令牌
NAPCAT_HTTP_URL=http://127.0.0.1:3001
NAPCAT_ACCESS_TOKEN=NapCat中配置的令牌
QQ_GROUP_IDS=群号1,群号2
BOT_TIMEZONE=Asia/Shanghai
BOT_DAILY_TIME=12:00
BOT_DAY_START=06:00
BOT_DAILY_EARLY_MINUTES=10
BOT_WEEKLY_TIME=20:00
BOT_REMINDER_MINUTES=30
BOT_DRY_RUN=true
```

上面的 3001 是示例端口，按 NapCat 实际 HTTP 服务配置填写。NapCat 监听本机地址，调用 OneBot `send_group_msg`，正文为 `group_id` 与文本 `message` 段数组；以实际安装版本验证鉴权和响应结构。必须同时检查 HTTP 结果、OneBot `status` / `retcode` 和返回的 `message_id`，不能仅凭 HTTP 200 判定发送成功。

先以 `BOT_DRY_RUN=true` 生成预览与日志，再在指定测试群验证。不同群可以配置不同游戏、赛事白名单和消息类型；第一版允许环境变量统一配置，后续再增加逐群配置文件。

### 发送记录与重启去重

Windows 使用独立的本地 SQLite，例如 `bot/data/delivery.sqlite`，只保存通知状态，不复制业务库。

建议 `deliveries` 字段：`id`, `group_id TEXT`, `event_key TEXT`, `kind`, `match_id`, `payload`, `payload_hash`, `status`, `attempts`, `next_attempt_at`, `message_id`, `created_at`, `sent_at`, `last_error`，并加 `UNIQUE(group_id, event_key)`。

- 日报键：`daily:日报归属日期:part序号`（无比赛日预告同样使用此键）；周报键：`weekly:周日日期:part序号`。一次计划的所有分段先持久化，重试沿用原分段，避免内容变动导致已发送部分错位。额外持久化每群每日期的日报计划及生成状态，防止提前发送后在 12:00 再生成另一份日报。
- 临赛键：`reminder:match_id:规范UTC开赛时间`。同一场改期后允许新时刻提醒。
- 变更键：`change:match_id:修订内容哈希`；另存已通知的对阵、时间、状态快照，只有通知过的比赛才推送更正。
- 领取任务与状态更新在本地事务中进行，配合单实例运行防止并发重复。
- 明确未发送的失败才自动有限重试，指数退避，临赛任务过了开赛时间即失效。
- 请求超时、连接中断或进程在“发送后记账前”退出时，可能已送达 QQ。此类记为 `unknown`，保留待核对，不盲目自动重发；重启时遗留 `sending` 也转为 `unknown`。OneBot 发送接口没有可依赖的业务幂等键，不能承诺严格恰好一次。
- 停机恢复后，日报/周报只在计划时刻后 2 小时内补发；临赛只发送仍未开赛且处于提醒窗口的消息，不补发过去多天通知。

## 5. 验收与部署顺序

1. 实现并测试时间可信标记、按游戏同步状态和专用接口；先备份生产库，再运行幂等迁移。
2. 自动化覆盖北京时间跨日、05:59/06:00 分界、早场提前 10 分钟、12:00 边界、次日凌晨纳入、仅次日凌晨有比赛、无比赛切换预告、提前发送后中午去重，以及 TBD、禁用赛事、过去的 upcoming、取消/延期、部分同步失败、分页超过 200 条、改期后重新提醒、重启去重及响应丢失。
3. Windows 配置网站地址与令牌，干跑预览日报、临赛消息和周预告；核对实际线上数据新鲜度。
4. 配置本机 NapCat HTTP 服务，在明确指定的测试群发送一条测试消息并核对回执。
5. 开启正式群推送，验证任务计划程序重启恢复；保存令牌于本机环境配置，日志脱敏。

实施时还需实际提供：网站域名、目标群号、NapCat HTTP 地址及版本。令牌应直接填入服务器环境配置，不需要在聊天中发送。本文默认时间、范围和样式可直接作为第一版配置。
